## Связь с ДЗ 2 и контракт результата

Потребитель — аналитик климата. Контрольный бизнес-вопрос: в какие дни 1–3 июня 2024 у Москвы, Сочи и Якутска суточная амплитуда температуры была наибольшей. Ответ — упорядоченные строки город × день UTC с амплитудой, минимумом, максимумом и средней температурой. Максимум контрольного среза — Якутск 1 июня, 16,5 °C.

Исходный факт ДЗ 2 — один час UTC в городе, ключ `(city_id, observed_at)`. Витрина `published.weather_daily` — один город × день UTC, ключ `(city_id, observed_date)`. Часовые температуры агрегированы по UTC, без перевода в местные сутки. Температуры и амплитуда — °C; суточная сумма осадков — мм; `n_hours` — число часов. Справочник города связан по `city_id`; контрольный срез использует неизменные атрибуты города.

## Запуск с нуля

Нужны запущенный Docker и Docker Compose. Порты 5000, 5001, 5435, 5436, 8018, 8019 должны быть свободны.

```bash
cd /Users/bminhojkhon03/projects/hse_master/data_storage/student-babaev-hw03
docker compose config --quiet
docker compose up -d --build
python3 scripts/run_all.py
python3 scripts/render_evidence.py
```

Первый полный запуск требует новых томов без базы `warehouse`. Повторный запуск `run_all.py` на заполненном стенде намеренно завершается без перезаписи. Для отдельного нового стенда можно использовать другой проект Compose и свободные внешние порты. Изменение `bootstrap.dcs` не переопределяет конфигурацию уже инициализированного DCS.

Последовательность полного сценария:

1. Дождаться рабочего лидера, потоковой реплики и маршрутизации записи.
2. Сохранить среду, сгенерировать синтетику, создать `warehouse`, загрузить CSV и обновить статистику.
3. Запустить независимый контроль, прогрев и пять повторов каждого исходного запроса.
4. Создать дополнительный индекс, проверить ответы, измерить оба запроса.
5. Создать секции с тем же дополнительным индексом, проверить всю таблицу через двусторонний `EXCEPT ALL` и измерить оба запроса.
6. Определить роли, записать и дождаться маркера на реплике, показать отказ записи, выполнить явный switchover и проверить старый и новый маркеры.
7. Выполнить опыт двух сессий на отдельной таблице `demo.mvcc_value`, завершить транзакции.
8. Сделать custom dump, создать новую `warehouse_restored_<UTC timestamp>`, восстановить и сравнить каталоги, все строки, ключи и оба отчёта.
9. Сохранить `evidence/completed.txt` только после успешного завершения всех проверок.

## Подключение и повтор отдельных проверок

Локальные учебные реквизиты: `postgres / postgres`. Клиент записи подключается к HAProxy `127.0.0.1:5000`, который проверяет Patroni `/leader`; чтение реплики — `:5001` через `/replica`. Роль не определяется именем контейнера.

```bash
docker compose exec -T node1 patronictl -c /tmp/patroni.yml list
docker compose exec -T node1 env PGPASSWORD=postgres psql \
  -h haproxy -p 5000 -U postgres -d warehouse \
  -c "SELECT pg_is_in_recovery(), current_setting('transaction_read_only');"
python3 scripts/equality.py --stage final
python3 scripts/independent_check.py
python3 scripts/patroni_demo.py
python3 scripts/mvcc_demo.py
python3 scripts/backup_restore.py
```

Повтор `patroni_demo.py` снова меняет лидера и использует свежие уникальные маркеры. Повтор `backup_restore.py` создаёт ещё одну отдельную базу и файл, сохраняя предыдущие. На обычном локальном стенде имя пользователя клиента задано открыто; подключения привязаны к loopback. Эти настройки предназначены для обучения.
